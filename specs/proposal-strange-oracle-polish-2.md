# 낯선 점술관 — 결제까지의 길 다시 짜기 + 팔 수 있는 수준으로 다듬기 (제안서 2)

작성: planner, 2026-09-30. 운영자 선택 전 단계다. 기획서(specs/strange-oracle.md)와 제품 코드는 고치지 않았다.
운영자 지시: "아이템은 신선한데 팔리기까지의 과정이 너무 길다. 어느 순간부터는 제한을 둬야 할 것 같다. 하지만 항상 다음이 궁금해서 결제까지 이어지도록."

**확인 방법**: 모의 서버 두 대(8787 mock, 8788 결제 꺼짐)를 띄우고 헤드리스 Edge 360x800(움직임 줄이기)으로 직접 돌렸다. 입구 → 오검 방(이름 입력 → 의식 → 결과) → 6/6 나의 이야기 → 결제 전 화면 → 모의 결제 → 책 112쪽 전부 넘김 → 새 탭 영수증 재열람 → 실패·오류 주소 → 결제 꺼짐 화면 → 법무 3쪽. 화면 글자는 전부 떠서 읽었고, 책은 오검 방 전체(6~18쪽)와 제2부·닫는 글(89~112쪽)을 통독했다.
**미확인**: 실제 기기, 움직임 켠 상태, 실제 토스 결제창·환불, 소요 시간 실측(아래 시간은 모두 추정), 유료 본문 전수 통독(오검·제2부만 읽음).

## 0. 요약: 가장 값진 세 가지

1. **결제 제안이 호기심이 가장 높은 순간에 없다.** 방 결과 끝의 책 한 줄은 "이 방의 네 장 전체는 여섯 문 끝 '한 권의 책'에 담겨요"(데칸 결과, mock)라고 말하고 링크는 미리보기로만 간다. 1/6에서 궁금해진 사람에게 "다섯 방 더 돌고 오세요"라고 하는 셈이다. → 1장 선택안.
2. **6/6에 닿았을 때 받는 제안이 "52분 더 읽기"다.** 읽기만 약 14분(tests.md:309, 분당 500자 가정) + 입력·의식 6번을 마친 사람에게 "약 2만 6천자 · 읽는 데 약 52분" 책을 판다. 무료로 이미 여섯 방 풀이를 다 읽어 배가 부른 상태다. → 1장 + 항목 1.
3. **돈을 낸 사람이 볼 흠이 남아 있다.** 책 112쪽(쪽당 평균 약 230자, 11~50자짜리 쪽 다수), 유료 본문 속 "이 리포트"·띄어쓰기 오타, 결제창에 찍힐 상품 이름 "더 깊은 이야기", 개인정보처리방침과 화면의 모순. → 2장 항목 1·2·6.

### 1-2. 선택안 비교

공통 전제: 상품은 하나(한 권의 책, 3,900원)로 유지한다. 가격·SKU를 늘리면 고지·약관·환불·영수증이 모두 늘어난다.
공통 기술 사실: 무료 풀이는 공개 파일(data-*.js)에 있고, 7장상 **유료로 바꾸는 글은 공개 파일에서 빼 서버로 옮겨야 한다.** "제한"의 비용은 거의 전부 이 이전 작업이다.

**6/6 전에 결제받을 때의 기술 조건 (A·C 공통)**
- 영수증 코드(주문번호)에는 여섯 방 결과가 다 들어 있어야 한다(core.js:237). Ⅰ~Ⅳ는 이름·생일로 정해지므로 결제 전 화면에서 계산할 수 있다. 룬·시빌라는 무작위 뽑기다(calc.js:139).
- **미리 봉인(추천)**: 결제하는 순간 남은 방의 돌·제비를 같은 난수로 먼저 뽑아 코드에 넣는다. 나중에 그 방에 들어가면 의식은 그대로 하고 봉인된 결과가 열린다. 서버·영수증 변경 0. 결제 전 화면에 "아직 가지 않은 방의 돌과 제비는 결제하는 순간 함께 뽑혀 책에 봉인돼요"를 적는다(돌려 말하지 않는다).
- 덤: 영수증 코드에 여섯 방 결과가 있으므로, 다른 기기에서 영수증으로 열면 여정도 함께 복원할 수 있다(이어가기 코드와 같은 효과).
- 대안(비추천): 결제 뒤 마친 방의 코드를 서버에 추가로 보내 책을 덧붙이는 방식. "토스가 확인한 주문번호 안의 코드로만 조립한다"는 서버 원칙(core.js:6)을 깨야 한다.

### 1-3. 추천: C를 지금 만들고, 관문(A)은 결제를 켜는 날 숫자를 보고 정한다

한 줄: **"언제든 열 수 있는 책 + 3/6 중간 결말"**. 운영자 직감(제한)에 가장 가까운 것은 A다. 그래도 C를 먼저 권하는 이유는 써 본 흐름에 있다.

1. **지금은 결제가 꺼져 있다.** A·B는 off에서 아무것도 바뀌지 않는다(바뀌면 막다른 길). 사업자등록 전까지 3~4일치 작업이 시험도 못 한 채 묵는다. C의 떡밥·중간 결말은 off 무료판에서도 "다음 방으로 가게 하는 힘"으로 바로 쓰인다.
2. **호기심은 방 결과 직후에 가장 높고, 지금 그 자리에 살 길이 없다.** 오검 결과 끝에서 책의 Ⅱ장 첫 문장("다들 눈치만 보던 회의실에서…")이 궁금해지는데 5개 방 뒤로 미뤄진다. 관문 위치를 옮기는 것보다 제안을 그 순간으로 옮기는 편이 길을 더 많이 줄인다(첫 결제 기회 약 17~20분 → 약 3~4분, 추정).
3. **어디서 떠나는지 모른다.** 3/6 전에 대부분 떠난다면 3/6 관문은 효과가 없고, 6/6까지 잘 온다면 관문이 효과 있다. 분석(결정 62) 없이 큰 재작업을 고르는 것은 도박이다.
4. **버리는 작업이 없다.** A로 가더라도 "6/6 전 결제(미리 봉인)·3/6 중간 결말·방 끝 잠긴 조각"은 그대로 A의 부품이다. C는 A의 1단계다.
5. "여섯 방 무료"라는 지금의 약속과 광고 심사용 분량을 건드리지 않는다.

A로 넘어가는 조건(운영자가 기준 숫자를 정함): 결제를 켠 뒤 "6/6 도달은 많은데 결제 전 화면 열람→결제가 낮다"가 보이면 관문을 세운다. 그때 입구 칩을 "세 방 무료"로 바꾸고, 촐킨·룬·시빌라 풀이를 서버로 옮긴다.
운영자가 지금 바로 제한을 원하면 A를 고르되, 순서는 같다(C 부품 → 문구 이전 → 관문).

### 1-4. "다음이 궁금하게" 만드는 장치 (추천안 기준, 화면·문구 자리)

새 화면은 만들지 않는다. 모두 기존 자리의 교체·상태 추가다. 문구는 data.js, 유료 문장은 한 글자도 공개 파일에 넣지 않는다.

규칙 확인
- 8장: 떡밥은 "무엇이 더 있는지"만 말한다. "놓치면", "지금 아니면", "당신만 모르는" 같은 불안·재촉 표현, 마감·한정 없음. 미래 쪽 방(촐킨·룬) 떡밥은 단정·예언형 금지. 정확도 과장 없음.
- 7장: 가격은 버튼마다 적는다. 결제 전 화면의 받는 것·분량·가격·환불 고지와 동의 체크는 그대로 거친다(방에서 누른 버튼도 결제 전 화면으로 간다, 바로 결제창 아님). 광고는 잠긴 조각 카드 바로 위아래에 두지 않는다.
- 6장: 결제 전 화면에서 남은 방(Ⅰ~Ⅳ) 계산에 이름·생일이 필요하면 그 자리에서 입력받아 계산에만 쓴다(지금 생일 입력 칸과 같은 방식). 서버로 가는 것은 여전히 결과 코드뿐.

### 1-5. "속았다"가 없게: 정직한 안내

- 입구 칩 "여섯 방 무료"는 C에서 참이다. FAQ "무료와 유료는 무엇이 다른가요?"에 한 문장 추가: "책은 언제든 열 수 있고, 열지 않아도 여섯 방과 나의 이야기는 끝까지 무료예요."
- A로 갈 때는 입구 칩을 반드시 "세 방 무료"로 바꾸고, 관문 화면에 "여기까지가 무료예요"를 첫 줄에 적는다. title·description·og 문구에 "무료"가 있으면 같이 고친다. off 기간에 여섯 방을 무료로 본 사람에게는 on 전환 뒤 달라진 점이 입구에서 보이게 한다.
- 6/6 전 결제자: "결제 시점의 결과로 책이 엮여요"(지금 문구)에 "아직 가지 않은 방은 결제 순간 뽑혀 봉인"을 더한다. 받는 분량 표기는 같다(책 전체).
- 미리보기의 "가상의 두 사람 견본" 표시는 유지한다(좋은 점: 지금도 정직하다).

## 2. 다듬기 항목 (새 구조에서도 유효한 것만)

### 1. 책이 112쪽이다 — 넘김 피로와 빈 쪽
- 근거: 쪽 수 112(재열람 111). 쪽당 글자 수가 제1부 200~300자, 시기별 흐름은 86~174자(91쪽은 "일" 한 항목 뒤 절반이 빈 종이). 11~50자 쪽: 4쪽(38자)·44·49·53쪽(34자)·56·68쪽(33자)·89·90쪽(표제만 두 장 연속). 3쪽→4쪽은 문장 중간("그리고 / 앞으로…")에서 끊긴다.
- 제안: ① 시기별 흐름은 한 구간(일·관계·배움·이동)을 한 쪽에 ② 남는 글이 50자 미만이면 앞 쪽 글자 간격 조정 또는 단락 단위로 넘기기 ③ 제2부 표제지와 "시기별 흐름" 표제지 합치기 ④ 본문 글자 크기 한 단계 조정 여부는 designer 판단. 목표 80쪽 안팎(추정).

### 2. 유료 본문·결제창의 옛 이름과 오타
- 근거: 여는 글 "이 리포트 끝까지"(4쪽), 닫는 글 "이 리포트를 다시 펼쳐"(111쪽, close.js 8곳 계열) — 화면은 "한 권의 책"으로 통일됨. 오검 Ⅲ장 "늘먼저 나서다 보니"(12쪽, 띄어쓰기). 결제창·카드 명세에 찍힐 상품 이름 `ORDER_NAME = "낯선 점술관 · 더 깊은 이야기"`(api/_lib/core.js:43). 표지 "6개의 문"(다른 곳은 "여섯 문").
- 제안: copywriter가 _paid 전체를 패턴 검색("리포트", 붙은 부사, 숫자 표기) + 방별 결과 2개씩 통독, ORDER_NAME은 developer가 "낯선 점술관 · 한 권의 책"으로. 서버 재시작·build-dist 필요.
- 효과: 돈 낸 사람이 처음 보는 흠 제거. 작업량: 소~중(copywriter, 전수 통독은 분량이 큼 — 약 140만 바이트). 위험: 없음. 전수 통독 여부는 미확인 상태로 둠.

### 3. 같은 말이 무료와 책에서 되풀이된다
- 근거: 오검(훼른) "함께 든 방패가 더 오래간다"가 나의 이야기 1장 요약, 책 Ⅲ장("혼자 버티는 것보다, 함께 버티는 게 더 오래가요"), Ⅳ장 끝 두 문단에 네 번. "한 사람을 초대"도 Ⅲ 끝·Ⅳ 끝 반복. 책 Ⅰ장은 방에서 읽은 핵심 풀이 그대로(고지에 "새 문장 약 2만 3천자"로 밝혀 둔 점은 정직하다).
- 제안: 본문 재작성은 하지 않는다. ① 책 Ⅰ장 머리에 "방에서 읽은 부분" 표시 + "Ⅱ장부터 읽기" 링크(developer, 소) ② copywriter가 방별 Ⅳ장 맺음 두 문단 중 요약과 겹치는 쪽만 덜어내는 표본 점검(결과 10개) 후 범위를 보고.
- 효과: "아까 읽은 건데" 느낌 감소. 작업량: 소 + 점검. 위험: 분량 표기(±15% 검사)와 맞물림.

### 4. 분량 숫자가 화면마다 다르다
- 근거: 결제 전 "약 25,776자 · 약 52분" / 고지 "약 2만 6천자" → 표지 "약 26,554자" → 목차 "약 2만 7천자 · 53분" → 영수증 재열람 표지 "약 26,136자".

### 5. 나의 이야기 6/6의 어긋난 문구와 맺음 없음
- 근거(6/6 화면): 부제 "낯선 방을 하나 지날 때마다 … 한 장씩 채워져요", 원형 설명 끝 "방을 더 돌수록 이 원형은 … 바뀔 수 있어요" — 더 돌 방이 없다. 여섯 요약 뒤 곧바로 책 카드로 끝나 무료 이야기의 맺음 문단이 없다. 같은 결과를 입구는 "버티는 방패", 나의 이야기는 "Fearn · 훼른"이라 부른다(데칸도 "마음을 읽는 이" / "게자리 · 둘째").

### 6. 결제 실패·오류 안내가 한 가지뿐이다
- 근거: 취소(PAY_PROCESS_CANCELED)와 카드 거절(REJECT_CARD_COMPANY) 모두 "결제창을 닫았거나 연결이 잠시 끊겼을 수 있어요". 승인 단계에서 서버가 400을 돌려줘도 "봉인을 여는 중에 연결이 끊겼어요 · 결제가 됐다면 책은 그대로 남아 있어요" + "다시 시도하기"만 반복되고 문의처가 없다(금액을 바꾼 주소로 재현. 실제 토스 오류 코드별 동작은 미확인).

### 7. 결제 꺼짐 화면의 "곧 열려요"

- 작업량: 소. 위험: 기존 e2e 기대값(off: "곧 열려요") 수정 필요. 기획서 D-9 변경이라 운영자 결정.

### 8. 영수증 코드: 30자, 경고가 약하다
- 근거: "SO10-0W5E-…-KN" 30자를 사람이 옮겨야 한다. 안내는 "코드를 아는 사람은 누구나 이 책을 볼 수 있으니 공유하지 마세요"뿐. 이 코드에는 이어가기 코드와 같은 결과 번호(데칸·촐킨·나크샤트라)가 들어 있어, 결정 36의 논리대로면 태어난 날을 알아낼 수 있다(직접 역산하지 않음, 미확인). 잃어버렸을 때 "결제 시각·금액으로 찾아 드려요"라고 약속하는데 운영자가 실제로 찾는 절차는 미확인.
- 제안: ① 경고를 이어가기 코드와 같은 수준으로 맞춤 ② "코드 복사" 옆에 "코드 카드 이미지 저장"(사용자 버튼, 기기 안 저장) ③ 분실 절차를 운영자가 토스 상점 화면에서 확인한 뒤 문구 확정.
- 작업량: 소. 위험: 6장 — 코드는 입력값에 준해 다룬다(자동 저장·전송 없음 유지).

### 9. 방 결과 화면이 길고 구성 순서가 방마다 다르다
- 근거: 3,500~4,850px. 카드 → 원형 → 방 고유 블록 → 핵심 풀이 → 표 → 상식 → 안내자 → 면책 → 글자 링크 3~4개 → 다리 → 다음 문. 별의 방은 "PLOT TWIST"·공감 카드 3개가 더 있어 가장 길고, 핵심 풀이 뒤에 맺음 문단이 표 아래 따로 떨어져 있다. 공유 버튼이 카드 아래와 하단 글자 링크에 두 번.

- 효과: 다음 문과 책 제안이 첫 두 화면 안으로 올라옴. 작업량: 중(designer+developer). 위험: 광고 자리(7장: 결과 문구·버튼 바로 옆 금지) 재확인.

## 3. 권장 순서

1. 운영자 선택: 1장 선택안(A/B/C), 미리 봉인 방식, 숨은 장 제목 공개 여부, off에서 책 카드 숨김.
2. planner: 고른 안을 기획서 11단계로 옮김(결정 44 개정) → 기획 검수.
3. 바로 할 수 있는 작은 것(구조와 무관): 항목 2·4·5·6·7.
4. 구조 작업: 장치 3·4·5(off에서도 보이는 것) → 미리 봉인·6/6 전 결제·장치 1·6·7 → 항목 9.
5. 책: 항목 1·3.
6. 결정 62(분석)를 먼저 풀면 A로 갈지 판단할 숫자가 생긴다. 분석 없이는 이 제안의 효과를 잴 수 없다.

## 4. 사업자등록 뒤 결제를 켜기 전 체크리스트 (운영자 몫)

- 결제 전 화면·법무 3쪽의 ◯◯ 채우기: 상호, 대표자, 사업자등록번호, 통신판매업 신고번호, 주소, 연락처, 호스팅 제공자, 부가세 표기, 미성년자 결제 안내, 환불 문의처·처리 기간·운영 시간, 시행일, 개인정보 보호책임자, 결제 기록 보관 기간, 청약철회 제한의 근거 조항.
- 법무 쪽 상단 "※ 운영자 확인 전 템플릿입니다" 문구 제거.
- 개인정보처리방침 제2조가 화면과 다르다: 방침은 "궁합 상대의 이름·생년월일 … sessionStorage로 잠시 저장"이라 하는데 화면은 "저장하지 않으며"라고 하고 실제로도 저장하지 않는다(e2e-paid D-5). 시빌라 질문 글은 방침에 없다. 주문번호에 담긴 결과 코드가 결제대행사에 전달·보관된다는 점과 그 코드의 성격(항목 8)을 어떻게 적을지 확정. 문구 초안은 copywriter가 고칠 수 있다.
- 이용약관 제1조 "서비스를 이용하면 동의한 것으로 봅니다"가 적절한지 확인(미확인, 법률 판단).
- 토스 계약·심사, 테스트 키 → 실제 키(환경 변수), PAY_MODE 전환, "모의 결제" 띠가 사라지는지 확인.
- 실제 기기에서 결제 1건 → 책 열람 → 다른 기기에서 영수증 재열람 → 환불 → 같은 코드가 막히는지(코드상 410 처리는 있음, core.js:258. 실제 동작 미확인).
- 분실 문의 대응 절차(토스 상점 화면에서 주문번호 찾기) 리허설.
- 결제창에 보이는 상품 이름(항목 2) 확인.
- A를 고른 경우: 입구·title·description의 "무료" 표기 교체, 공개 파일에 유료 글 0건(build-dist 검사) 확인.

- 결제를 서둘게 하는 장치(마감·한정·카운트다운), 불안을 건드리는 떡밥.
- 결정 62(분석·광고) 구현 — 운영자 결정 33~35 대기.
- 10단계에서 끝난 것(이어가기 코드, 링크 복사, 입구 첫 3초, 책 두 쪽 미리보기, 이름 통일 화면 문구).

## 6. 운영자가 정할 것

1. 선택안 A / B / C (추천 C, A는 결제 켠 뒤 숫자로 판단). 결정 44 개정 여부.
2. 6/6 전 결제의 "미리 봉인" 방식 허용 여부.
3. 숨은 장 제목을 무료 떡밥으로 공개할지.
4. 결제 꺼짐에서 책 카드·FAQ 유료 문답을 숨길지(D-9 변경).
5. 영수증 코드 경고를 "태어난 날을 알아낼 수 있어요" 수준으로 올릴지.
