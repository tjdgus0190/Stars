## 1. 페이앱 개요

### 1-1. 무엇인가
- 운영사는 (주)유디아이디다. 사이트 메뉴에 "유디아이디 제안서"가 있다. 법인명 표기는 운영자가 계약서에서 확인한다.
- 금융위원회에 등록된 전자결제대행(PG)이고, 2024년 기준 가맹점은 약 9만 곳이다(검색 요약).
- 사업자등록이 없는 개인도 판매자로 가입해 카드·간편결제를 받을 수 있다. 비사업자 거래 내역은 주민등록번호로 국세청에 신고된다(검색 요약).

### 1-2. 개인(비사업자) 가입 조건·수수료·정산 (payapp.kr 「비용안내」「구비서류/심사」「정산안내」 원문)

| 항목 | 내용 |
|---|---|
| 가입 구분 | 법인사업자 / 개인사업자 / **개인판매자(비사업자)** |
| 개인판매자 수수료 | 카드·간편결제 **4.0%**, 휴대폰 소액결제 4.0%, 계좌이체 2.3%, 가상계좌 220원(VAT 별도 여부는 표 머리에 "VAT 별도"로 보임, 운영자 확인) |
| 단서 | "실물결제 기준이며, **비실물의 경우 수수료가 인상될 수 있습니다.**" 우리 책은 비실물이다. 인상 폭은 **미확인**이다 |
| 가입비·유지비 | 초기등록비 120,000원(무료 이벤트로 0원), 유지비 0원. 이벤트가 언제까지인지는 미확인 |
| 첫 정산 조건 | 첫 정산 때 계약서류를 낸다. 서류 검토와 함께 "간단한 업종심사"를 한다. 심사는 영업일 약 2일, 끝나면 전화로 연락한다 |
| 개인판매자 서류 | 날인한 계약서 2부, 신분증 사본(앞·뒤), 통장 사본 1부. 이메일·우편·전자계약서 중 하나로 낸다 |
| 정산 주기 | 기본 D+3영업일(2026-09-01 적용 예정이라고 적혀 있음). **"비실물/리스크 업종은 D+5일"**. D+1 빠른 정산은 별도 신청 |
| 보증보험 | 결제 규모와 업종에 따라 요청할 수 있다. "**콘텐츠**, 방문판매, 해외결제 등 유의업종이나 리스크 업종은 … 보증보험 가입을 요청 드릴 수 있습니다." 요청을 받으면 보험증권이 나온 뒤에 정산된다 |

계산 예: 3,900원 카드 결제 1건, 수수료 4.0%와 VAT 별도를 가정하면 약 3,728원이 남는다(3,900 − 156 − 15.6). 비실물 인상률은 반영하지 않았다.

### 1-3. 디지털 콘텐츠 판매 가능 여부
- 「등록 심사 업종 기준」 팝업 원문을 보면 다음과 같다.
  - **불가업종**: 경마·경륜, 대출, 도박·성인, 선불카드, 환금성, 의약품 등
  - **리스크업종**(수수료 인상): 로또번호 생성 서비스, **부적**, 성인 콘텐츠, 웹하드, 아이템, 호스팅·광고 등
  - **유의업종**(수수료 인상 가능): 게임, 소프트웨어, 온라인강의, **정보 서비스** 등
- **운세·점술 콘텐츠는 어느 목록에도 이름이 없다.** 불가업종은 아니다. 다만 "정보 서비스"(유의)나 비실물로 분류될 가능성이 높다. 그렇게 되면 수수료 인상, D+5 정산, 보증보험 요청이 따라올 수 있다. 실제 분류는 **미확인**이고 업종심사에서 정해진다.
- "업종 심사에 따라 당사 이용이 불가할 수 있으며 해당 사유로 결제가 취소될 수 있습니다."라는 문구가 있다. 그래서 **live 전에 운영자가 업종 확인을 받아야 한다**(4장).
- 우리 책에는 부적 판매가 없다. 만신의 방 연출에도 부적 상품이 없다. 가맹 신청 설명에 "부적 판매가 아님"을 분명히 적기를 권한다.

### 1-4. 가맹 심사가 사이트에서 보는 것
- 공개 안내 페이지에서는 사이트 표시 요건(사업자 정보·환불 정책 표시 등)을 찾지 못했다(**미확인**). 서류와 업종심사만 적혀 있다.
- 다만 법률상 표시 의무는 따로 있다(4장). 우리 사이트에는 이미 이용약관·개인정보처리방침·구매·환불 안내(legal 3종)가 있으므로, 심사 전에 결제 문단을 채워 두면 된다.

## 2. 연동 방식 (docs.payapp.kr 개발 문서 원문)

### 2-1. 결제 요청: 세 가지
| 방식 | 내용 | 우리에게 |
|---|---|---|
| **JS** | `<script src="https://lite.payapp.kr/public/api/v2/payapp-lite.js">` 를 불러와 `PayApp.setDefault('userid', …)`, `PayApp.setParam('goodname'|'price'|…)`, `PayApp.payrequest()`(또는 `call()`)로 결제창을 연다. "임의로 변경할 경우 연동이 원활하지 않으며 최신 업데이트가 적용되지 않습니다" → 스크립트를 복사해 두지 말고 공식 주소에서 불러야 한다 | **추천** |
| REST | 서버가 `https://api.payapp.kr/oapi/apiLoad.html`에 `cmd=payrequest`로 요청하고, 받은 결제창 주소로 보낸다. **`recvphone`(구매자 휴대폰 번호)이 필수**다 | 비추천: 휴대폰 번호를 우리 화면에서 받아 우리 함수로 보내야 한다(6장 부담) |
| 링크·QR | 판매자 화면에서 만든 고정 결제 링크 | 비추천: 결제마다 우리 쪽 식별값(var1)을 붙일 수 없어 자동 확인이 안 된다(미확인) |

- JS 방식에서 `recvphone`을 비워 두면 결제창에 입력 칸이 뜨고, 구매자가 그곳에 직접 넣는다(문서: "빈값으로 입력될 경우 사용자가 직접 입력할 수 있는 입력박스가 결제창에 표시됩니다"). 휴대폰 번호는 우리 화면을 거치지 않는다.
- 주요 요청 값은 다음과 같다.
  - `goodname`: 상품명
  - `price`: 1,000원 이상
  - `feedbackurl`: 결제 통보 주소
  - `returnurl`: 결제 완료 뒤 이동 주소, **POST로 이동**
  - `var1`·`var2`: 임의 값, 통보 때 그대로 돌아옴
  - `checkretry=y`: 통보 실패 시 최대 10회 재시도
  - `smsuse=n`: 결제요청 문자 안 보냄
  - `openpaytype`: 결제수단 제한(card, kakaopay, naverpay, phone 등). 판매자 설정이 우선한다
  - `skip_cstpage=y`: 매출전표 페이지를 건너뜀
- `goodname`·`memo`에는 URI 주소를 넣을 수 없다.
- 결제 취소 API(`paycancel`, 정산 뒤 `paycancelreq`)는 있다. **결제 상태를 조회하는 API는 문서에 없다.** 그래서 결제 확인은 오직 결제 통보(feedbackurl)로만 할 수 있다. 3장 설계는 이 사실에서 출발한다.

### 2-2. 결제 통보(feedbackurl)
- 페이앱 서버가 우리 주소로 **POST**를 보낸다. 받는 값은 아래와 같다.
  - 판매자 확인: `userid`, `linkkey`, `linkval`
  - 상품·금액: `goodname`, `price`
  - 구매자: `recvphone`(휴대폰 번호)
  - 결제: `pay_date`, `pay_type`, `pay_state`, `mul_no`(결제요청번호)
  - 우리가 보낸 값: `var1`·`var2`
  - 카드명·승인번호·카드번호 일부 등. 결제수단별 필드는 "추가될 수 있음을 고려"하라고 되어 있다
- `pay_state` 값
  - 1 = 요청
  - **4 = 결제완료**
  - 8·32 = 요청취소
  - 9·64 = 승인취소
  - 10 = 결제대기(가상계좌 입금 전)
  - 70·71 = 부분취소
- JS 방식에서 feedbackurl을 쓰면 **요청 상태(pay_state=1)로 먼저 통보가 온다.** 여기에 `SUCCESS`로 답해야 결제가 진행된다.
- 응답 규칙: HTTP 200이고 본문이 `SUCCESS`여야 성공이다. 이 페이지에서 다른 페이지로 이동(302·자바스크립트)시키면 안 된다.
- 같은 통보가 여러 번 올 수 있다. 문서는 "`mul_no`, `var1`, `var2`를 이용해 중복방지"하라고 한다.
- **위변조 확인**
  - 판매자 관리 화면의 "연동 KEY"·"연동 VALUE"와 통보로 온 `userid`·`linkkey`·`linkval`이 같을 때만 정상 호출이다.
  - 여기에 더해 요청 금액(`price`)이 우리가 정한 금액과 같은지 확인하라고 한다.
  - 서명(HMAC) 방식이 아니라 **공유 비밀값 비교** 방식이다. 그래서 `linkkey`·`linkval`은 함수 환경 변수에만 두고, 저장소·화면·로그에 절대 두지 않는다(CLAUDE.md 10장).
  - 통보를 보내는 IP 목록은 문서에서 찾지 못했다(미확인).
- **테스트 모드**: 별도 샌드박스나 테스트 결제 모드 안내는 **없다.** 문서 예제의 `payapptest`는 견본 아이디다. 그 아이디로 실제 시험 결제가 되는지는 미확인이다.
  - 그래서 에이전트는 모의 서버에서 "가짜 결제창 + 가짜 통보"로만 시험한다.
  - 실제 결제 확인은 운영자가 live 전에 본인 결제 1건을 하고 판매자 화면에서 취소하는 방식으로 한다(4장).

### 2-3. CLAUDE.md 3장 예외에 맞는가
- 3장 원문: "결제대행사 공식 결제 SDK(예: 토스페이먼츠)는 그 회사 공식 주소에서, 결제 버튼을 누른 뒤에만 불러올 수 있다."
- 페이앱은 등록 PG(검색 요약)이고, `lite.payapp.kr`은 페이앱 공식 주소다. **"결제하기"를 누른 뒤에 `<script>`를 동적으로 붙이면 3장에 맞는다.** 첫 화면·책 목차에서는 불러오지 않는다. off·test 배포판에서는 아예 넣지 않는다.
- 버전을 고정할 수 없다(주소에 v2만 있음). 3장의 "버전 고정"은 CDN 라이브러리 규칙이다. 결제 SDK 예외 문장에는 버전 조건이 없으므로 위반으로 보지 않는다. 다만 QA가 같은 판단을 하는지는 미확인이므로 질문 2에 함께 묻는다.
- 서버 쪽: 3장 예외는 "결제 승인 확인과 유료 콘텐츠 전달에 필요한 최소한의 서버리스 함수"다. 함수는 맞는다. 하지만 **결제 기록 저장소는 문구에 없다**("서버, DB 없음"). 3장 설계상 기록이 반드시 필요하므로 운영자 판단이 필요하다(질문 1·2).

## 3. 흐름 설계 (지금 구현을 최대한 재사용)

### 3-1. 왜 기록이 필요한가
- 결제가 끝났다는 사실은 **페이앱 → 우리 함수**(통보)로만 온다. 페이앱에는 상태 조회 API가 없다.
- 그런데 책을 받을 사람은 **브라우저**다. 통보를 받은 함수 인스턴스와 브라우저가 묻는 인스턴스는 다를 수 있고, 지금 함수는 메모리만 쓴다.
- 그래서 "통보 → 브라우저"를 이어 줄 **아주 작은 공유 기록**이 하나는 있어야 한다.
- `returnurl`로 돌아올 때 페이앱이 결제 값을 함께 POST하는지는 미확인이다. 함께 오더라도 브라우저를 거친 값이라 믿을 수 없다(`linkval`이 들어 있다면 오히려 노출 문제다).

### 3-2. 기록을 둘 곳 비교

| | 안 A. 서명 토큰만(기록 없음) | **안 B. Netlify Blobs 최소 기록 (추천)** | 안 C. Cloudflare Workers + D1 |
|---|---|---|---|
| 방법 | 결제마다 서명된 열람 토큰을 만들어 기록 없이 서명만 확인 | 같은 Netlify 사이트의 키-값 저장소. 결제 1건 = 작은 키 2개 | 결정 95에서 친구 궁합 지도용으로 정한 서버·DB를 결제에도 씀 |
| 동작하나 | **안 됨.** 토큰을 만들 수 있는 곳은 통보를 받은 함수뿐이다. 그런데 그 토큰을 브라우저에 넘길 길이 기록 없이는 없다. 서명은 "재열람 확인"에만 쓸 수 있다 | 됨. 통보 함수가 쓰고, 브라우저가 묻는 함수가 읽는다 | 됨 |
| 새로 드는 것 | — | `@netlify/blobs` 패키지 1개(루트 `package.json`, Netlify가 함수 묶을 때 설치). 함수를 v2 형식으로 바꾸거나 v1 호환 연결을 씀(v1 지원은 공식 문서에 명시 없음, 미확인) | 두 번째 호스팅, 다른 출처 호출(CORS), 계정 2곳 |
| 일관성 | — | 기본은 "60초 안 전파"다. 결제 확인에는 **strong 일관성**을 켠다(문서에 선택지 있음) | 강함 |
| 저장 위치 | — | 사이트 전체 저장소 기본 us-east-2(AWS). 국외 저장 → 처리방침에 적는다 | Cloudflare(국외) |
| 15단계와 관계 | — | 결제와 지도가 다른 저장소가 된다 | 한 곳으로 모인다. 그러나 15단계는 CLAUDE.md 개정 뒤에 시작한다(결정 95). 결제를 그 개정에 묶으면 늦어진다 |
| 무료 한도 | — | 무료 플랜 한도는 문서에서 찾지 못함(미확인). 키 수가 판매 건수 × 2라 작다 | 미확인 |

**추천은 안 B다.** 이미 쓰는 Netlify 안에서 끝나고, 패키지 1개와 함수 수정으로 된다. 안 A의 서명 아이디어는 쓰지 않는다. 열람 코드를 해시로 저장하면 같은 일을 더 단순하게 하기 때문이다.

### 3-3. 기록에 두는 것 (개인정보 없음)
- 기록 1: `pay/<sha256(R)>` → `{ mul_no, state, passHash, at }`. R은 브라우저가 만든 무작위 결제 확인값이다(3-4).
- 기록 2: `pass/<passHash>` → `{ mul_no, state }`
- 두지 않는 것
  - 휴대폰 번호(`recvphone`), 카드 정보, `linkkey`·`linkval`, IP
  - 이름·생년월일·시각·성별·결과 코드는 처음부터 받지 않는다
- 통보로 들어온 나머지 필드는 읽지 않고 버린다. `console`에 본문을 찍지 않는다.
- 보관 기간 [기본값]: 열람 코드는 무기한(소장형 콘텐츠). 취소된 건은 `state`만 바꾼다. 삭제 시점은 운영자 결정이다. 전자상거래법상 거래 기록 보관 의무(대금 결제 기록 등)는 판매자에게 있다. 그 기록은 페이앱 판매자 화면에 남는다. 우리 저장소가 그 의무를 대신하는지는 법률 확인이다(미확인).

### 3-4. 결제 → 책 흐름
1. **결제 전 화면**(지금 `#screen-deeper` 재사용)
   - 받는 것·가격·결제 방법·환불을 보여 주고 동의 체크를 받는다.
   - 버튼을 "구매하러 가기"(외부 새 탭)에서 **"3,900원 결제하기"**로 바꾼다.
2. **버튼을 누르면**(브라우저)
   - ① 무작위 128비트 R을 만든다(`crypto.getRandomValues`, 입력값과 무관).
   - ② `sessionStorage`의 `strange-oracle-payreq`에 R을 둔다. 탭을 닫으면 사라진다. 입력값이 아니므로 6장 예외 대상은 아니다. 그래도 "내 정보 지우기"로 함께 지운다.
   - ③ 그다음에야 `payapp-lite.js`를 동적으로 불러온다.
   - ④ 결제창을 연다. 넘기는 값은 아래와 같다.
     - `userid`, `shopname`
     - 고정 `goodname`("낯선 점술관 한 권의 책"), `price` 3900
     - `feedbackurl` = `https://<사이트>/api/pay/feedback`, `returnurl` = `https://<사이트>/api/pay/return`
     - `var1` = R, `checkretry=y`, `smsuse=n`, `skip_cstpage=y`
     - `openpaytype`: 질문 3의 결과
     - **`recvphone`은 넘기지 않는다.**
3. **페이앱 → 함수 `pay`(feedback)**
   - `userid`·`linkkey`·`linkval`을 환경 변수와 상수 시간 비교한다.
   - `price === 3900`, `goodname` 일치를 확인한다.
   - 상태별 처리
     - `pay_state=1`(요청): 기록 없이 `SUCCESS`만 답한다.
     - `pay_state=4`(완료): 열람 코드 P를 만든다. P = `SOP`+12자+검사 1자로, 지금 모양 그대로다. P는 R과 서버 비밀값 `PASS_SECRET`로 HMAC 파생한다. 그래서 원문을 저장하지 않아도 3-4의 4에서 다시 계산할 수 있다. 기록 1·2를 쓰고 `SUCCESS`를 답한다. 같은 `mul_no`가 다시 오면 덮어쓰지 않고 `SUCCESS`만 답한다.
     - `8·9·32·64·70·71`(취소): `mul_no`로 찾아 `state`를 `cancelled`로 바꾼다.
     - `10`(가상계좌 대기): 기록하지 않는다. 가상계좌는 열지 않기를 추천한다(질문 3).
     - 확인에 실패하면 `SUCCESS`가 아닌 응답을 준다(재시도 대상). 원인은 로그에 남기지 않는다.
4. **브라우저가 돌아옴**
   - `returnurl`은 POST라 정적 페이지가 받지 못할 수 있다(Netlify 정적 파일이 POST에 어떻게 답하는지 미확인).
   - 그래서 함수 `pay`(return)가 받아 `303`으로 `…/products/strange-oracle/#paid`에 보낸다. 받은 POST 본문은 읽지 않는다.
   - 화면은 `sessionStorage`에 R이 있으면 `POST /api/pay/status { r: R }`을 부른다.
     - 기록 1이 `paid`면 함수가 P를 다시 계산해 `{ pass: P }`를 준다(`Cache-Control: no-store`).
     - 아직이면 `{ state: "pending" }`을 준다. 화면은 2초 간격으로 최대 30초 묻는다.
     - 그래도 없으면 "결제 확인이 늦어지고 있어요" 한 줄과 [다시 확인]·[목차로] 버튼을 보인다. 막다른 곳은 0개다.
5. **열람**: P를 받으면 지금의 `writePass(P)` → `loadPaid(file)` → 함수 `book`을 그대로 쓴다.
   - 함수 `book`의 확인을 하나 늘린다. 지금은 "환경 변수 해시 목록"만 본다. 여기에 **"Blobs의 `pass/<hash>`가 있고 `state=paid`"**를 더한다.
   - 환경 변수 목록은 운영자 수동 코드(문의 대응·보상용, `make-pass.js`)로 남긴다.
6. **코드 보여 주기**: 열람이 열리면 화면에 P를 크게 보이고 [복사] 버튼을 둔다. 안내는 "다른 기기·나중에 다시 볼 때 이 코드를 넣어요. 적어 두거나 캡처해 두세요"다.
   - 다시 볼 때는 지금의 "이미 샀어요 · 열람 코드 넣기" 칸을 그대로 쓴다.
   - 코드를 잃어버렸을 때는 문의처(39번)에 결제일·금액을 알려 주면 운영자가 판매자 화면에서 `mul_no`를 찾는다. 그 뒤 수동 코드를 발급한다. 이 경로는 개발 범위 밖이고 운영 절차다.

### 3-5. 재열람과 6장
- **열람 코드(SOP)를 그대로 재사용한다.**
  - 지금은 회차 공용 코드였다. 앞으로는 **결제 1건 = 코드 1개**다.
  - 코드 모양·입력 칸·오입력 안내(SO1·SOG)·틀린 시도 제한(IP 메모리 10분 10회)·`strange-oracle-pass` sessionStorage·"내 정보 지우기"는 모두 그대로다.
- 서버로 가는 것
  - 페이앱으로: 고정 상품명·금액·R. 구매자가 결제창에 직접 넣는 휴대폰 번호·결제수단 정보는 페이앱이 받는다.
  - 우리 함수로(브라우저에서): R, 열람 코드, 장 묶음 이름뿐이다.
  - 우리 함수로(페이앱에서): 결제 통보다. 이 안에 휴대폰 번호가 들어 있지만 저장·기록하지 않는다(처리방침에 적음).
  - **이름·생년월일·태어난 시각·성별·결과 유형 코드는 페이앱에도 우리 함수에도 가지 않는다.** 3장 예외("결제 정보와 결과 유형 코드만")보다 좁다.
- localStorage·쿠키·URL에는 아무것도 두지 않는다. R은 `var1`로 페이앱 결제창 주소·통보에 실린다. 하지만 R은 입력값이 아닌 무작위 값이다.

## 5. 운영자가 할 일과 질문

### 5-1. 운영자 계정·확인 작업 (에이전트는 하지 않음)
1. **페이앱 판매자 가입**(개인판매자 또는 사업자, 질문 4) → 판매자 화면 「설정」에서 연동 KEY·VALUE 확인 → 결제수단 설정(질문 3).
2. **업종 확인 먼저**: 고객센터에 "생년월일로 보는 운세·점술 읽을거리(디지털 텍스트) 3,900원, 부적 판매 아님"이 받을 수 있는 업종인지, 분류(일반/유의/리스크)와 수수료·정산 주기·보증보험 요청 여부를 묻는다. 받은 설명(2026-10-16)에 이 문장을 넣는다.
3. 계약서류 제출(개인판매자: 계약서 2부·신분증·통장 사본).
4. 세무·법률 확인
   - 사업자등록 필요 여부와 간이과세 가능 여부
   - 통신판매업 신고 면제 해당 여부
   - 사이트에 표시할 판매자 정보 범위
   - 디지털 콘텐츠 청약철회 표시 문장
5. Netlify 환경 변수 넣기: `PAYAPP_USERID`·`PAYAPP_LINKKEY`·`PAYAPP_LINKVAL`·`PASS_SECRET`(무작위 32바이트 이상)·`PASS_MODE`. 저장소·문서·대화에 값을 쓰지 않는다.
6. data.js `pay.payapp.userid`·`shopname`, `site.url`, legal ◯◯ 값(문의처 39번 포함)을 알려 준다.
7. **실결제 시험 1건**(live 직전, 본인 카드)
   - ① 통보가 오는지
   - ② 책이 열리는지
   - ③ 코드로 다른 기기에서 다시 열리는지
   - ④ 판매자 화면에서 취소하면 코드가 막히는지
   - ⑤ `returnurl` 복귀가 휴대폰(카카오페이 앱 전환 포함)에서 되는지
8. GitHub 저장소 비공개 확인(62번)과 `release` 병합 흐름은 그대로다.

### 5-2. 질문 (선택지, 추천 표시)

**질문 1. 결제 기록을 어디에 둘까요?** 페이앱에 결제 조회 API가 없어 결제 1건당 작은 기록이 꼭 필요합니다(3-1).
- A. **Netlify Blobs**: 지금 Netlify 안에서 끝나고, 결제번호·상태·코드 해시·시각만 둠, 개인정보 없음 **(추천)**
- B. Cloudflare Workers + D1: 결정 95의 지도 서버와 한곳에 모음. 단, 15단계 CLAUDE.md 개정과 함께 묶여 결제가 늦어짐
- C. 기록 없이 운영자 수동 발급: 페이앱 알림을 보고 운영자가 코드를 보내 줌. 연락처를 받아야 하므로 6장과 맞지 않고 자동 열림도 안 됨(비추천)

**질문 2. CLAUDE.md 3장에 결제 기록 저장을 어떻게 적을까요?** 지금 3장은 "서버, DB 없음"이고 예외는 "서버리스 함수"뿐이라, 기록 저장소는 문구에 없습니다(10장: 규칙이 모호하면 묻는다).
- A. 예외 문장에 한 줄 추가 **(추천)**: "결제 승인 확인에 필요한 최소 기록(결제번호·결제 상태·열람 코드 해시·시각)만 같은 호스팅의 키-값 저장소에 둘 수 있다. 개인정보(휴대폰 번호·카드 정보·입력값)는 저장하지 않는다. 결제 SDK는 결제사 공식 주소의 최신 판을 쓰며 버전 고정 대상이 아니다."
- B. "결제 승인 확인"에 기록이 포함된다고 보고 문구는 고치지 않음(QA가 위반으로 볼 수 있음)
- C. 개정하지 않음 → 페이앱 자동 확인은 할 수 없음

**질문 3. 어떤 결제수단을 열까요?** (`openpaytype`, 판매자 설정이 우선)
- A. **신용카드·카카오페이·네이버페이(·토스페이 등 간편결제)** **(추천)**: 바로 승인, 3,900원에 맞음
- B. A + 휴대폰 소액결제: 수수료는 같은 4.0%(비실물 인상 별도). 대신 취소·환불 처리가 까다롭다는 일반적 이야기가 있다(미확인)
- C. 모든 수단(가상계좌 포함): 입금 대기(`pay_state=10`) 처리가 더해짐(비추천)

**질문 4. 사업자등록·통신판매업 신고는 어떻게 할까요?** (세무·법률 확인 결과에 따라)
- A. **간이과세 사업자등록 후 사업자로 페이앱 가입** **(추천)**: 7장 출시 전 절차를 문구 그대로 지킨다. 간이과세자는 통신판매업 신고 면제일 수 있다(면제 확인 전에는 신고 쪽이 안전). 카드 수수료 우대(영중소)는 국세청 매출 자료가 생긴 뒤에만 적용된다고 적혀 있다
- B. 개인판매자(비사업자)로 시작 + CLAUDE.md 7장에 "개인판매자 PG 가입" 예외 추가: 빨리 시작할 수 있음. 수수료 4.0%. 계속 판매가 사업소득으로 볼 여지가 있어 세무 확인 필요
- C. 확인이 끝날 때까지 결제는 test에 두고 배포판은 off 유지(어느 쪽이든 그 사이 기본 상태)
