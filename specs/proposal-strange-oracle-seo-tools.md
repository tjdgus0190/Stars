# 제안서: 검색으로 들어오는 입구와 무료 계산 도구 (낯선 점술관)

- 작성: planner, 2026-11-13
- 상태: 운영자 선택 전 (CLAUDE.md 9장: 운영자가 고른 뒤 기획서 `specs/strange-oracle.md`에 단계로 반영)
- 계기: 운영자 "광고 없이도 유입이 될 수 있는 것들". 비슷한 서비스(삐삐사주, ppippi.me)와 비교했을 때 부족한 두 가지를 다룬다.
  - **A. 검색으로 들어올 입구가 없다**
  - **B. 무료 도구가 없다**
- 이 제안서는 비교에서 확인한 사실과 이 저장소의 현재 상태만 근거로 쓴다. 검색량·순위처럼 확인하지 못한 것은 "미확인"으로 적는다.

## A. 검색 입구 페이지 (방마다 하나씩, 따로 된 주소)

### A-1. 무엇을 만드나
1. **기본 검색 설정 (모든 페이지 공통)**
   - 키워드 중심 제목·설명
   - `canonical`
   - 절대 주소 `og:image`
   - JSON-LD(WebSite + 페이지별 WebPage/FAQPage)
   - 사이트 전체 `sitemap.xml`, `robots.txt`
2. **방별 입구 페이지 7개.** 각각 따로 된 정적 HTML이고, 검색어 하나를 중심으로 한다.

| 주소(안) | 중심 검색어 후보(검색량 미확인) | 이어지는 방 | 페이지 내용 |
|---|---|---|---|
| `/saju/` | 무료 사주풀이, 사주 보는 법, 일간 | Ⅰ 만신의 방 | 사주 여덟 글자·일간 설명, 열 일간 한 줄씩, FAQ |
| `/vedic/` | 인도 점성술, 베다 점성술, 나크샤트라 | Ⅲ 베다의 방 | 달의 집 27개 목록과 한 줄 뜻, 서양 별자리와 다른 점 |
| `/rune/` | 룬 점, 룬 문자 뜻 | Ⅵ 룬의 방 | 룬 24자 목록과 뜻, 세 개 뽑는 법 |
| `/maya/` | 마야 달력, 마야 탄생일, 촐킨 | Ⅴ 촐킨의 방 | 20개 날 기호와 13 숫자, 260일 순환 |
| `/egypt/` | 이집트 별자리, 데칸 | Ⅳ 데칸의 방 | 별자리를 셋으로 나눈 36 데칸, 생일 표 |
| `/ogham/` | 켈트 나무 문자, 이름 점 | Ⅱ 오검의 방 | 오검 20자와 나무, 이름 소리로 찾는 법 |
| `/oracle/` | 신탁, 질문 점, 예스 노 점 | Ⅶ 시빌라 신탁의 방 | 시빌라 예언서 이야기, 질문하는 법 |

3. **페이지 하나의 구성** (7장 광고 심사 기준 "300자 이상 소개 글"도 함께 채운다)
   - 검색어가 들어간 `<h1>` → 소개 300~600자 → 목록·표(예: 나크샤트라 27개) → 그 방의 전설 한 단락
   - 자주 묻는 질문 3~5개
   - **[이 방의 문 열기]** 버튼: 해당 방으로 바로 가는 링크(`/products/strange-oracle/#<방>`)
   - 다른 여섯 방으로 가는 내부 링크
4. **첫 화면 제목·설명 바꾸기 (안)**
   - 제목: "낯선 점술관 — 무료 사주풀이 · 인도 점성술 · 룬 · 마야 달력, 일곱 점술로 보는 나"
   - 브랜드 이름은 앞에 그대로 두고 뒤에 검색어를 붙인다. 최종 문구는 copywriter가 정한다.

### A-2. 규칙 확인
- **순수 정적 HTML·CSS·JS** (3장): 빌드 도구·서버 없음. 입구 페이지는 손으로 쓴 HTML이다.
- **화면 문구는 data 파일에** (3장): 입구 페이지 문구는 `data-guide.js` 한 파일에 모은다(문구만, 로직 없음). 표처럼 긴 내용은 기존 `data-runes.js`·`data-stars.js` 등을 다시 쓴다.
- **유료 문장 금지** (7장): 입구 페이지에는 무료 문구만 쓴다. `tools/build-dist.js`의 유료 문장 지문 검사가 새 페이지에도 돌게 한다.
- **입력값 없음**: 입구 페이지는 읽는 페이지라 사용자가 입력하는 칸이 없다(계산은 B에서).
- **면책 문구**: strange-oracle은 면책 문구를 넣지 않는 예외(8장)가 있다. 입구 페이지도 같은 제품이므로 같은 예외를 따른다(운영자 확인 필요, §D-4).
- **광고** (7장): 넣을 수 있는 화면이다. 넣을지는 운영자가 정한다(§D-3).

### A-3. 주소를 어떻게 둘까 (운영자 결정 §D-1)
- **안 1 (추천): 짧은 주소**
  - 파일은 `products/strange-oracle/guide/<page>/index.html`에 두고, `netlify.toml`에서 짧은 주소(`/saju/` 등)로 보여 준다(200 rewrite, 주소창은 짧은 주소 그대로).
  - `canonical`도 짧은 주소로 둔다.
  - 장점: 검색 결과에 깔끔한 주소가 보인다.
- **안 2: 긴 주소**
  - `/products/strange-oracle/guide/saju/` 그대로 쓴다.
  - 설정이 하나 줄지만 주소가 길다.

## B. 무료 계산 도구 (이미 있는 계산 코드를 화면으로 꺼낸다)

### B-1. 무엇을 만드나

| 도구 | 쓰는 코드(이미 검증됨) | 입력 | 무료로 보여 줄 것 | 더 보려면 |
|---|---|---|---|---|
| **B1 무료 만세력** | `saju.js` + lunar-javascript 1.7.7 | 생년월일, 태어난 시각(모르면 빼기), 양력/음력 | 네 기둥(년·월·일·시) 간지, 일간, 오행 개수 | 만신의 방: 일간 풀이·흐름 |
| **B2 나크샤트라 계산기** | `astro.js` + Astronomy Engine 2.1.19 | 생년월일, 태어난 시각, 태어난 곳(시간대) | 달의 집(27개 중 몇 번째), 라시(달 별자리), 한 줄 뜻 | 베다의 방 |
| **B3 마야 탄생일** | `calc.js` `tzolkin` | 생년월일 | 날 기호 + 숫자(예: 7 재규어), 한 줄 뜻 | 촐킨의 방 |
| **B4 이집트 데칸** | `calc.js` `decan` + `astro.js` 태양 황경 | 생년월일 | 내 별자리 속 데칸(앞·가운데·끝), 한 줄 뜻 | 데칸의 방 |
| **B5 이름 오검** | `calc.js` `nameToOgham` | 이름(한글) | 이름 소리에 맞는 오검 글자와 나무 | 오검의 방 |
| **B6 룬 한 개 뽑기** | `data-runes.js` | 없음(누르기만) | 룬 하나와 짧은 뜻 | 룬의 방: 세 개 뽑기 |

- **결과 화면 구성:** 결과 카드 → 짧은 설명 → **[○○의 방에서 이어서 읽기]** → 결과 이미지 저장·공유(기존 `common/share-card.js`·`share-buttons.js`).
- **이어 읽기:** 방으로 넘어갈 때 다시 입력하지 않게 하려면 6장 예외(sessionStorage, 탭을 닫으면 사라짐, 처음 저장할 때 안내, "내 정보 지우기")만 쓴다. 주소에는 넣지 않는다.
- **우선순위:** 검색량이 클 것으로 짐작되는 B1(만세력)과 B2(인도 점성술)를 먼저 만든다(검색량 미확인).

### B-2. 개인정보 (6장, 가장 중요)
- **계산 위치:** 모든 계산은 브라우저 안에서만 한다. 서버 호출 없음.
- **저장 금지:** 입력값(생년월일·시각·이름·성별)을 주소(URL)·쿠키·localStorage·분석 이벤트에 넣지 않는다.
  - 그래서 "결과 주소 공유하기"는 만들지 않는다.
  - 공유는 결과 이미지와 "나도 해 보기" 링크(입력값 없는 도구 주소)로만 한다.
- **분석 이벤트:** 도구 이름과 결과 유형 코드까지만 보낸다(예: `tool_result`, `tool=maya`, `type=jaguar_7`). 생년월일은 보내지 않는다.
- **방으로 이어 가기:** sessionStorage 예외만 쓴다(위 B-1).
- **시험:** 기존 개인정보 시험(e2e의 "birth privacy" 검사)을 도구 페이지에도 똑같이 돌린다.

### B-3. 정확도 (3장)
- 사주·천체 계산은 지금 제품과 같은 라이브러리·같은 코드를 그대로 쓴다. 따로 새로 구현하지 않는다.
- tests.md의 대조 표본(만세력 대조, Meeus 대조)을 도구에도 다시 돌려 같은 값이 나오는지 확인한다.
- 화면에 "정확도 100%" 같은 과장은 쓰지 않는다(8장).

## C. 어떻게 잴까 (유입 효과 확인)
- **GA4 이벤트**(6장 범위 안): `guide_view`(페이지 이름), `tool_result`(도구·결과 코드), `tool_to_room`(어느 방으로 넘어갔는지), `guide_to_room`.
- **검색 등록:** 구글 서치 콘솔·네이버 서치어드바이저에 사이트와 sitemap을 등록하고, 검색어별 노출·클릭을 본다(계정 작업은 운영자, §D-6).
- **판단 시점:** 등록 후 4주 뒤 노출·클릭이 생긴 페이지를 보고 다음 페이지(고민별 입구 등)를 정한다. 검색 반영에 걸리는 시간은 미확인이다(보통 수 주로 알려져 있음).

## D. 운영자가 정할 것
1. **주소 방식:** 안 1 짧은 주소(`/saju/`) vs 안 2 긴 주소. 추천은 안 1.
2. **첫 화면 제목·설명 바꾸기:** 브랜드 뒤에 검색어를 붙이는 데 동의하는지.
3. **광고:** 입구·도구 페이지에 광고(애드센스·애드핏)를 넣을지. 넣으면 7장 규칙(한 화면 2개, 결과·버튼 옆 금지)대로 한다.
4. **면책 문구 예외 적용:** 입구·도구 페이지도 strange-oracle의 "면책 문구 넣지 않음" 예외(8장)를 그대로 적용할지.
5. **만세력 범위:** 네 기둥·일간·오행 개수까지만 보여 줄지, 대운 표도 보여 줄지. 추천은 대운 없이 시작하는 것이다(무료 범위가 넓어지면 만신의 방으로 넘어갈 이유가 줄어든다).
6. **계정 작업 (운영자만 가능):** 서치 콘솔·서치어드바이저 등록, 사이트 소유 확인 메타 태그 값 전달, 키워드 검색량 확인(네이버 키워드 도구).
7. **우선순위:** 아래 단계 순서가 괜찮은지.

## F. 하지 않는 것
- 결과를 주소에 담아 공유하는 기능(6장 위반)
- 입력값을 서버로 보내는 서버 렌더링(3장·6장)
- 검색어만 잔뜩 넣은 숨김 글(검색 엔진 정책 위반 위험)
- 삐삐사주의 문구·이름·디자인을 따라 쓰는 것(참고는 구조까지만)
