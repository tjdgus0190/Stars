# 제안서: 낯선 점술관 결제 — 포스타입(국내)·딜리헙(해외) 계획

- 작성: planner, 2026-10-15. 운영자 결정 85·86·90의 1차 산출물. **운영자가 고르기 전 단계의 문서다.**
- 관련 기획: `specs/strange-oracle.md` 「14단계」 14-4(시험 모드 흐름은 이 문서의 어느 안에도 맞게 만든다).
- 조사 방법: 2026-10-15 웹 검색·공개 페이지. 검색 요약으로만 본 것은 "(검색 요약)"으로, 확인하지 못한 것은 **미확인**으로 적는다. 플랫폼 약관 원문은 운영자가 계정에서 다시 확인해야 한다.

## 1. 왜 플랫폼 판매인가
- 운영자는 사업자등록이 없어 PG(토스페이먼츠) 직접 계약 결제를 걷어 냈다(결정 75 배경). 포스타입·딜리헙 같은 창작자 플랫폼은 플랫폼이 결제를 받고 창작자에게 정산하므로, PG 계약 없이 3,900원 판매를 시도할 수 있다.
- 대가: 우리 사이트와 구매가 **직접 연결되지 않는다**(아래 3장). 그래서 "구매 → 열람 확인"을 열람 코드로 잇는다.

## 2. 두 플랫폼의 판매 구조

| 항목 | 포스타입 | 딜리헙 |

| 구매자 결제 수단 | 카카오페이·카드·네이버페이·토스페이·가상계좌·**페이팔(해외 사용자만)**·앱스토어로 포인트 충전(검색 요약, [다음 기사](https://v.daum.net/v/Vp8i3PJ6Uy)) | 미확인 |

## 3. 연결 방식: 왜 열람 코드인가
- 구매 확인 API가 없으면 우리 서버는 "이 사람이 샀는지"를 물어볼 곳이 없다. 그래서 **구매자에게만 보이는 곳(유료 포스트 본문)에 열람 코드를 넣고**, 구매자가 그 코드를 우리 화면에 넣으면 서버리스 함수가 코드를 확인해 유료 장을 준다(14-4).
- 서버로 가는 것: 열람 코드와 장 묶음 이름뿐. 이름·생일·시각·성별·결과 코드는 가지 않는다(CLAUDE.md 6장, 3장 서버리스 예외 "결제 정보와 결과 유형 코드만"보다 더 좁다).
- 코드 원문은 저장소·문서에 쓰지 않는다. 운영자가 시험 도구로 코드와 해시를 만들고, 해시는 호스팅 환경 변수에, 코드는 판매글에만 넣는다(10장).

## 4. 판매 방식 비교

| | 안 1. 공용 열람 코드 | 안 2. 회차별 판매글·회차 코드 **(추천)** | 안 3. 리포트 자체를 판매글로 |
|---|---|---|---|
| 방법 | 판매글 1개. 본문 유료 구간에 코드 1개. 정해진 주기(예: 한 달)마다 **글을 고쳐** 새 코드로 바꾼다 | 기간마다 판매글을 새로 연다(예: "낯선 점술관 한 권의 책 · 2026년 11월"). 회차마다 다른 코드. 회차가 끝나면 그 글은 판매를 멈추고, 구매자 소장본에는 그 회차 코드가 남는다 | 원형 8종(또는 장별) 리포트를 판매글로 올린다. 우리 사이트는 "내 원형은 ◯◯ → 이 글"로 링크만 |
| 서버 함수 | 필요 | 필요 | **불필요**(`pay.verify = "none"`) |
| 개인화 | 있음(일곱 방 결과로 엮은 책) | 있음 | **없음**(같은 원형이면 같은 글) — 지금 책의 장점이 사라짐 |
| 코드 공유 위험 | 코드 하나가 퍼지면 교체 전까지 누구나 열람 | 한 회차 코드만 퍼진다. 그 회차만 폐기하면 된다 | 없음(플랫폼이 막음) |
| 기존 구매자 재열람 | 글을 고치면 구매자가 **최신본을 보는지 소장본(옛 코드)을 보는지 미확인**. 옛 코드를 바로 끊으면 기존 구매자가 못 열 위험 | 소장본의 회차 코드가 계속 유효 → 재열람 확실. 폐기할 때만 그 회차 구매자 안내 필요 | 플랫폼 소장본으로 재열람 |
| 운영 부담 | 교체 때 코드 생성·환경 변수·글 수정 | 회차마다 글 복제·코드 생성·환경 변수 추가(월 1회 약 10분 예상, 추정) | 원형 8편 작성·등록, 갱신 시 8편 수정 |
| 유출 대응 | 즉시 교체 → 기존 구매자 혼란 가능 | 해당 회차 코드 폐기 + 그 회차 글에 "새 코드" 추가(글 수정이 반영되는지 미확인 → 반영 안 되면 문의처로 안내, 39번 필요) | — |

- 코드 모양: `SOP` + 무작위 12자(Crockford Base32, 약 60비트) + 검사 1자. 추측으로 맞히기는 현실적으로 불가능하다. 함수는 인스턴스 메모리에서 접속 IP별 10분에 10회 넘게 틀리면 잠시 거부한다(저장 없음, 개인정보처리방침에 적음, specs 14-4). 응답은 `Cache-Control: no-store`.
- 다른 코드 오입력: 옛 영수증 코드(SO1)·이어가기 코드(SOG)를 열람 코드 칸에 넣으면 서버에 묻지 않고 각자 안내 한 줄(specs 14-4).
- 코드 유효 기간: 안 2는 **기본 무기한, 유출 확인 시 폐기**. 안 1은 교체 뒤 옛 코드 90일 유예 [제안].

## 6. 해외(딜리헙): 언어·통화와 창구 바꾸기
- **언어 [제안]**: 4차 순서대로 영어 → 일본어 → 중국어 간체·번체. 판매글은 언어마다 따로(딜리헙의 다국어 지원 방식 미확인).
- **통화 [제안]**: 딜리헙이 USD를 지원하면 **USD 2.99**(3,900원 근처, 끝자리 .99 관행). 지원 통화가 다르면 운영자가 3,900원 상당으로 정한다. 지원 통화·환율·결제 수단 모두 미확인.
- **창구 바꾸기 흐름(4차에 켬, 1차는 설정 칸만)**
  1. 화면 언어 결정: 수동 언어 선택이 있으면 그것, 없으면 `navigator.languages` 첫 항목(결정 86 에이전트 기본값, IP 조회 없음).
  2. 결제 전 화면의 구매처: 한국어 → 포스타입(`pay.stores.ko`), 그 밖 → 딜리헙(`pay.stores.global`). 결제 전 화면에 "다른 구매처로 사기" 글자 링크 1개(한국에 사는 외국인, 해외에 사는 한국인).
  3. 열람 코드 칸은 하나. 코드는 구매처마다 다르게 발급하되(접두어 같음) 같은 함수가 확인한다. 어느 구매처 코드인지는 서버 환경 변수에만 있다.
  4. 고지 문구(가격·환불)는 구매처마다 다르게 data.js에 둔다.
- 대안: 포스타입이 페이팔 충전을 받으므로 해외도 포스타입 하나로 가는 길이 있다. 단 포스타입 화면이 외국어를 지원하는지 미확인이라, 딜리헙 확인 결과를 보고 고른다.

## 7. 운영자가 할 계정·확인 작업 (에이전트는 하지 않음)
1. 포스타입 가입·본인 인증·**개인 크리에이터 인증**, 출금 계좌 등록. 판매 약관·수수료·원천징수·환불 정책 원문 확인, 1P = 1원인지 확인.
2. **시험 구매 1회**(본인 다른 계정 또는 지인): ① 판매글 유료 구간에 넣은 글이 구매 뒤에만 보이는지 ② 판매 뒤 글을 고치면 기존 구매자에게 고친 내용이 보이는지(안 1·2의 유출 대응에 필요) ③ 판매 중지한 글을 기존 구매자가 계속 볼 수 있는지.
3. 세무·법률 확인: 플랫폼 개인 판매에서 사업자등록·통신판매업 신고가 필요한지, 우리 사이트에 어떤 판매자 표시를 해야 하는지(specs 45·54번). 결과에 따라 CLAUDE.md 7장 개정.
4. 문의처(이메일) 정하기 — live 전 필수(specs 39번).
5. 서버리스 함수 호스트: GitHub 연결 Netlify 배포로 정해졌다(결정 93). Netlify 설정·push, 환경 변수에 코드 해시 넣기. **GitHub 연결 첫 push 전에 저장소가 비공개인지 확인**(기존 커밋 기록에도 유료 원본이 있음, specs 62번). 운영 브랜치는 `release`, QA "배포 가능" 뒤에만 병합(specs 63번).
5-1. **플랫폼 정책 확인(live 전 필수, CLAUDE.md 우선순위 2)**: 포스타입·딜리헙 약관이 "외부 사이트에서 쓰는 열람 코드만 담은 판매글"(외부 서비스 이용권 판매)을 허용하는지 확인한다. 허용하지 않으면 안 1·2는 쓸 수 없고 안 3(리포트 자체를 판매글로)만 남는다.
6. `tools/strange-oracle/make-pass.js`(14단계에서 developer가 만듦)로 회차 코드·해시 만들기 → 해시는 환경 변수, 코드는 판매글.
7. (4차) 딜리헙 가입·해외 판매 조건(언어·통화·정산·사업자 요건·세금) 확인, 같은 시험 구매.

## 8. 추천안
- **국내: 포스타입 + 안 2(회차별 판매글·회차 코드)**. 이유: API가 없어도 동작하고, 개인화된 책을 지킬 수 있으며, 글 수정 반영 여부(미확인)와 상관없이 기존 구매자 재열람이 확실하고, 유출 피해가 한 회차로 묶인다. 회차는 월 1회로 시작한다.
- **해외: 4차에 딜리헙을 같은 방식으로**. 딜리헙 조건이 확인되지 않으면 포스타입(페이팔) 단일 창구를 대안으로 둔다.
- **안 3은 대체안**으로만 둔다: 함수 운영이 끝내 어렵거나, 코드 공유가 받아들일 수 없는 수준일 때.
- live 전환 조건(모두 충족): 위 7장의 1~6과 5-1(플랫폼 정책), specs 50·54·39·62번 결정, 14단계 QA "배포 가능". 결정 92(13단계판 배포 안 함)로 옛 책 문장은 공개된 적이 없으므로, 3차 리포트 고도화를 기다릴 필요는 없다.
- 1차 배포판은 결제 화면을 숨긴다(결정 94, `pay.mode = off`). live 때 운영자가 `pay.mode`를 바꾸고 build-dist의 off 검사를 함께 푼다(specs 14-4).
